## Mapvideo главнее этого пилота

**Строжайшее условие.** На сервере уже работает проект **mapvideo**. Он главнее comm-assistant. Пилот не имеет права его ломать, останавливать или «чуть подкрутить».

Запрещено без явной письменной просьбы человека в этом чате:

- заходить в репозиторий, код, `.env`, тома и конфиги mapvideo и что-то там менять;
- останавливать, перезапускать, удалять, переименовывать контейнеры и процессы mapvideo (`mapvideo-frontend`, `mapvideo-backend`, `mapvideo-postgres`, `mapvideo-martin`, `mapvideo-osrm` и любые другие с этим именем);
- занимать порты mapvideo: **3000, 3001, 3002, 5432, 5000** и прочие, которые он уже слушает;
- команды вроде `docker compose down` / `docker stop` / `docker rm` / `docker system prune` / правка общесерверного nginx или systemd, если есть шанс задеть mapvideo;
- убивать процессы mapvideo. **GPU (RTX 5090) целиком наш** — mapvideo карту не использует; его процессы всё равно не убивать.

Разрешено только своё: каталог `/root/communication-assistant` (и его git), свои контейнеры этого compose, порты **3010, 5433, 8088**.

Не уверен, что команда безопасна для mapvideo — не выполнять, спросить человека. Если всё же задели — сразу написать человеку и откатить **только своё**; mapvideo не «чинить на глаз».

Подробности: [ARCHITECTURE.md §3.1](ARCHITECTURE.md#31-сосуществование-с-mapvideo) и правило `.cursor/rules/05-mapvideo-priority.mdc`.

## Закрытые решения

Не менять молча (полный список: [ARCHITECTURE.md §19](ARCHITECTURE.md#19-решения-которые-считаются-закрытыми)):

- модель по умолчанию — уже лежащий Qwen3.6-35B-A3B Q4_K_XL;
- порты **3010 / 5433 / 8088**;
- секреты только в `.env`.

Мелочи UI и имена отелей можно выбирать. Смену закрытого решения — сначала правка `ARCHITECTURE.md`, потом код.

## Как вести этап

1. Прочитать [docs/stages/README.md](docs/stages/README.md) и файл нужного этапа.
2. От актуального `main` создать ветку `stage/NN-slug` из файла этапа. В `main` напрямую не коммитить.
3. Делать **только этот этап**. Не забегать вперёд.
4. Написать автопроверки из файла этапа и прогнать их.
5. Красные тесты — чинить самому. Не чинится — откатить ветку и начать иначе. Не пушить сломанное в `main`.
6. UI или живая почта — **остановиться** и отдать человеку инструкцию из файла этапа. Не считать «и так сойдёт».
7. Когда автопроверки зелёные (и ручная проверка пройдена или в этапе явно «руками не просим»): один или несколько понятных коммитов.
8. `gh pr create` с заголовком `[stage NN] …`, в теле — что сделано и какие тесты гонялись.
9. Агент **сам мержит** PR в `main`, когда проверки зелёные. Дальше чинит сам, если после merge что-то упало: hotfix-ветка или revert-PR.
10. `git push --force` в `main` запрещён. Force на своей ветке до merge — только если ветку ещё никто кроме агента не использует.

Пока нет `origin` или git не инициализирован — не притворяться, что PR создан. Написать человеку: нужен remote и доступ к GitHub.

## Команды

Только этот репозиторий и его compose. Не останавливать mapvideo. Порты: сайт 3010, наша БД 5433.

```bash
npm install
cp .env.example .env   # локально, не коммитить; задать POSTGRES_PASSWORD и SESSION_SECRET

./scripts/up.sh          # llama-server в tmux (commassist-llm) + Docker db/web/worker
./scripts/down.sh        # выключить пилот; том Postgres остаётся
./scripts/up.sh --build  # пересобрать образы сайта и воркера
tmux attach -t commassist-llm   # логи модели; отцепиться: Ctrl-b d
# чужие tmux-сессии (wan22 и т.п.) не трогать

# Разработка на хосте, без контейнера сайта (не вместе с commassist-web):
docker compose up -d db
npm run db:migrate
npm run db:seed
npm run lint
npm test
npm run dev
npm run worker
```



## Тест-гейт

- Нет зелёных автопроверок этапа — нет коммита и нет PR.
- Нет автотеста на то, что должно проверяться глазами (вёрстка, «письмо дошло») — не закрывать этап, дать человеку чеклист из файла этапа.
- Живой Gmail и живую модель в unit-тестах не дергать: фикстуры и моки. Интеграцию с GPU — по возможности, не вместо юнитов.
- Перед PR: lint + test (+ то, что перечислено в этапе).



## Секреты

- `.env` не коммитить. В git только `.env.example` с пустыми паролями.
- Пароли приложений Gmail не писать в md, issues, логи, скриншоты, чат.
- Не читать `gmail_imap_test.py` в коммиты и не цитировать из него пароли.
- В логах обрезать тела писем.



## Когда звать человека

Писать прямо и по шагам, как в файле этапа. Типичные случаи:

- заполнить `.env` (пароли почты, секреты сессии);
- отправить или принять тестовое письмо;
- посмотреть UI / графики / «письмо в ящике клиента»;
- разрешить запуск `llama-server` на хосте, если GPU-контейнер не встал;
- дать доступ к GitHub / `git remote`;
- подтвердить снос **нашего** тома Postgres (не mapvideo);
- любое действие, которое может задеть mapvideo;
- всё, к чему у агента нет доступа.

Не звать человека, чтобы он писал код за агента, если агент может сделать сам.

## Definition of done этапа

- Чеклист файла этапа выполнен.
- Автопроверки зелёные.
- Ручная проверка пройдена или в файле этапа её нет.
- PR `[stage NN]` влит в `main`.
- В handoff: что слито, какие тесты, что осталось на человеке, какой следующий этап.



## Откат

- До merge: `git reset` / удаление своей ветки, данные справочника — `--force` сида или очистка таблиц этапа.
- После merge: revert-PR в `main` или fix-forward на новой ветке. Не переписывать историю `main`.
- Не дропать том Postgres с живыми письмами без явной просьбы человека.
